# 需求澄清

目标：PRD 中的每条需求都有可验证的验收标准和用例，人可以批准。

## 每一轮

1. 读 `docs/PRD.md`，找出含糊、缺失、相互矛盾的地方。
2. 一轮最多问 5 个问题，优先问会改变范围或验收方式的问题。
3. 把问答追加到 `## 澄清记录` 章节，每轮一个标题：

   ```markdown
   ### 2026-01-15 第 1 轮
   - Q: 是否支持离线使用？ A: 支持，联网后同步。
   ```

4. 人当场答不上来的问题登记为待澄清项，答复后改为 Closed 并写 Resolution：

   ```markdown
   ### OQ-001 离线数据保留多久
   - Status: Open
   - Relates: FR-003
   ```

5. 把结论写进需求，不要只留在澄清记录里。

## 必须问的问题

- 未来哪些东西会变化？对每个回答，登记一条 Type 为 Scenario 的 NFR（字段 Adds、Allowed-Paths、Closed-Modules），或在非功能需求章节明确写"不预留扩展"。
- 每条需求的失败情况和边界情况是什么？它们会成为 E、B 类用例。

## 需求格式

```markdown
### FR-003 离线同步
- Status: Active
- Release: 1
- Priority: P0

- AC-003-1: 断网期间的修改在联网后 30 秒内同步到服务器。
  - AC-003-1/N1: 断网修改 1 条记录，联网后服务器可见
  - AC-003-1/E1: 联网后服务器拒绝写入，本地保留修改并提示
  - AC-003-1/B1: 断网期间修改 1000 条记录
```

- 验收标准写可观察的结果，不写"快速""友好""适当"之类无法验证的词。
- 每条验收标准至少一个 N 类用例；有失败可能的写 E 类，有边界的写 B 类。
- 编号只增不删：删除需求时把 Status 改为 Removed，删除用例时在用例文字前加 `Removed`。
- 新术语登记到 `## 统一语言` 表格，正文统一使用术语，不用禁用别名。
- `init` 生成的示例需求、示例非功能需求与示例术语是格式示例，澄清后替换或删除。

## 结束

运行 `harness check prd term`，修复全部违规。然后告诉人：PRD 可以评审，批准请在终端执行 `harness approve prd`。代理不能批准，也不能执行这条命令。
